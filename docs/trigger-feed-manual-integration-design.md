# 誘発検出・Feed・マニュアル操作の合流設計とQA

2026-09-13。旧基準 `e0c98b4`、実装先 `/private/tmp/onedeck-solo-cockpit`。承認済みの統合設計と出荷記録。1–11節は設計・事前QAの要求と判断を残し、12節に実装済みの範囲・検証・出荷結果を記す。QA表の全項目が実対戦で確認済みという意味ではない。

## Goal / Non-goals / What stays untouched

カードの出来事に気づき、発生源と理由を確認し、必要な誘発をスタックへ置き、既存の手動操作で解決し、その結果と戻し方をFeedで追えるようにする。自動検出・手動登録・既存のマナ支援が同じ誘発を二重に処理しないことを中心の受け入れ条件とする。

全Oracleの自動解決、一般の置換効果の自動適用、旧storeへの復帰、別エンジンは非目標。公開は当初対象外だったが、追加指示により実施対象となった。既存CockpitClient→サーバーtransaction→applyTableOperation、マスター権限、各防御者の操作範囲、非公開投影、保存・Undo/Redoの原則を維持する。永続化とprojectionの拡張は必要だが、UIで独自の正本を持たない。

今回のユーザー指示は旧誘発検出・Feedの合流を含む。以前の「初回経路から一般誘発の自動進行を外す」という段階的除外を、今回の作業対象から除外する理由にしない。ただし、検出することと効果を勝手に実行することは別である。

## 2. 一つの処理経路

確定操作 → 意味のある出来事 → 誘発検出 → 未処理一覧／Feed → 対象・順番の確認 → スタック登録 → 既存の手動解決 → 完了記録。

- UIからのクリックや再描画を検出の入口にしない。サーバーが操作を受理した経路で一度だけ行う。
- Feedはこの状態の表示。確認・登録・除外は既存の確定操作と同じ権限・revision検証を通す。
- 手動のカード移動・ドロー等も出来事を作る。自動検出を「自動操作のときだけ」に限定しない。
- ただし「移動」と「破壊」「生け贄」、「ライフ減少」と「ダメージ」などを同一視しない。操作が表していない原因を最終盤面から推測して埋めない。
- バッチの最終差分だけでは、途中で出て戻ったカード、複数回のドロー、途中のフェイズを復元できない。既存操作の意味が確定する箇所から、順序と同時性を持つ小さい出来事を集める。アプリ全体をevent sourcing方式へ作り直す必要はない。

## 3. 保持する最小の情報

以下は実装前の論理モデル。旧GameEvent、PendingTrigger、ObjectSnapshotを先に照合し、意味が一致する型・collectorを再利用する。新しい汎用イベントframeworkは作らない。

| 記録 | 必要な情報 |
| --- | --- |
| 出来事 | 一意ID、確定操作との関連、操作内の順序／同時グループ、種類、関係席、必要な前後のobject snapshot |
| 誘発の一回分 | 出来事ID、発生源object ID・snapshot、能力行、検出時controller、発生回数、検出の対応範囲、登録可能な区切り、処理状態 |
| スタック登録 | 誘発IDとの関連、既存TableStackEntry、登録順・対象・必要な選択 |
| 対応状況 | 未確認／登録済み／手動登録へ関連付け済み／候補除外、必要なら簡潔な理由 |
| Feed | 確定結果から導く表示文と参照。ローカルの開閉や既読はゲーム上の対応状況とは別 |

IDは発生源の物理カードIDだけで作らない。同じカードの出入り、同じ能力の複数回発生を区別する。候補IDはaccepted operationの一意識別子と操作内の安定した索引等から作り、再送で新しい候補を増やさない。クライアントが送ったsource snapshotを権威にせずサーバー側の確定時snapshotを使う。

出来事の長期全保存は不要。Undo範囲と未処理・解決中の参照が必要とする記録を保全し、表示済みの古い履歴は有界にする。切り詰めで未処理候補や一回制限の根拠を消さない。履歴上限とセッション容量に対する実測をQAに含め、具体的な上限は実装時に既存25MB制限へ収まる根拠を持って定める。

## 4. 検出を自動化して、判断を支える

検出結果を二段階に分ける。

- 対応済みの条件・出来事から確定できる誘発: 理由と回数を示し、対象や順番を選んでスタックへ置く。ここでも効果はまだ実行しない。
- 複雑な条件や不足した出来事情報のため確認が必要な候補: 「要確認」として表示。根拠のない自動登録・自動ブロックをしない。未対応であることを検出漏れなしの保証へ読み替えない。

phase/turnの進行時には、登録が必要な対応済み誘発を先に扱う。解決中に生じた誘発はその解決を中断して積まず、適切な優先権の区切りまで保持する。既存の手動卓でSBAや優先権を自動判定できない区切りは「卓で確認」の明示的な操作として扱い、自動適法判定済みにしない。

確度の低い候補があるだけで普段の全操作を止めない。一方、登録が必要な誘発を黙って飛ばして次フェイズへ進めない。sandboxとして訂正して進む場合は、候補除外の明示操作と記録を残す。

主操作の優先順位は「現在の解決を終える／戻る → 登録可能な未処理誘発を扱う → 既存スタックの解決 → 戦闘・フェイズ進行」とする。旧primaryActionの「スタックがあれば常に先に解決」という表示テストを、そのまま今回の規則として移植しない。既存スタックが残っていても優先権の区切りで登録すべき誘発は先に扱う。登録順と候補の確認状態を、単なるバッジ件数で代用しない。

## 5. 手動操作との重複を防ぐ

### 候補を見てから処理する

候補の「スタックへ」で既存の能力・対象の作業面を開く。登録成功と候補の処理済み化を一つのtransactionで確定する。取消は下書きだけを取り消し、候補は残す。登録失敗も候補を残す。

実装上は、候補IDと対象・順番を受ける登録操作、既存項目への関連付け操作、候補除外操作を最小の拡張候補とする。候補の消去と既存activateを別々に送る構成にはしない。現在のactivateはcardOf(sourceId)から現在のcontrollerと本文を取り直すため、検出済み誘発の登録にそのまま使えない。登録はサーバー保存の候補snapshotからTableStackEntryを作り、支払・対象表示など意味の一致する部分だけを共用する。

### 手動登録を先に行った

手動の誘発登録面に、同じ発生源・能力に関する未処理候補を表示する。「この候補として登録」または「別の誘発として登録」を明示的に選べるようにする。既にあるスタック項目へ後から関連付ける場合も、候補IDと項目IDを検証する確定操作にする。

名前や本文が似ているだけで勝手に消し込まない。二回誘発したものを一回に潰さない。同じ候補を二つのスタック項目に関連付けない。一回分は一つの項目へ対応する設計を基本とし、複数回のまとめ登録は回数と各項目IDを保持する。

### 効果を手動で反映した

Feedの「手動処理」は、その発生源を保持した既存の解決作業へ進む入口にする。ドローやライフ操作を見ただけで「この誘発は処理済み」と推測しない。完了は明示操作。必要に応じて操作を解決中の項目と関連付け、結果を追えるようにする。

### 候補を外す

旧UIの「誘発を全て無視」をそのまま復活させない。「候補から外す」を確認できる位置に置き、対象と理由を記録する。ルール上必須の誘発が任意になったという表現にしない。「may」は通常、誘発を作らない自由を意味しない。未対応の卓上訂正と規則上の選択を区別する。

## 6. Feedの触り心地

上端のベルを本来のFeed入口へ戻す。接続・保存はメニューへ残す。バッジは未処理候補・要確認を示し、単なる過去ログで増やし続けない。

通常は閉じ、必要時に「未処理」「要確認」「記録」を同じ面に表示する。各行はカード名、短い出来事、回数、状態を中心にする。詳しい根拠・本文・対象は展開する。例えば「《発生源》｜他のクリーチャーが戦場へ｜2件」。選択肢は「スタックへ」「手動登録と対応」「候補から外す」。

旧Feedの候補優先・ログ新着順を保ちつつ、既存CockpitWorkPanelの「盤面を見る」と下書き保持を使う。Feedを閉じる・読む・既読にする行為は候補を消さない。発生源が墓地へ行っても、そのときのカードと本文を確認できる。

複数候補は発生源で見やすく束ねても、内部の一回分を保持する。同時誘発の順序はユーザーが確認する。単独で選択不要なら短い経路で登録するが、複数候補の見た目の並びをそのまま登録順とみなさない。

音は候補の再表示・Feed開閉・再接続では鳴らさない。既存マナの自動処理と通常の手動処理の違いを記録で読めるようにする。表示するFeed行の数と、意味イベントの音の数を同一にしない。

## 7. CRに関する設計根拠

リポジトリ固定版 `rule/Magic_The_Gathering_Comprehensive_Rules.txt` を参照する。

- 603.2: 誘発した段階では効果を実行しない。検出／登録／解決を分ける。
- 603.2c: 一つの出来事内の複数の発生を区別する。「one or more」を個々のカード枚数へ機械的に展開しない。
- 603.3、117.5: スタックへ置く区切りと、解決中に起きた誘発の待機を区別する。
- 603.3b–d: APNAP、同一controllerの順序、モード・対象などの選択。現行のマスター権限は誘発のcontrollerそのものではない。
- 603.4、603.5: 介在ifの再確認と、mayの効果を解決時に選ぶことを区別する。
- 603.6、603.10: 場所を離れた発生源とLKIを扱う。現在のカード状態だけを使わない。
- 605.1b等: 誘発型マナ能力は通常スタックと区別。既存planTableManaTriggersで対応済みの処理を再実行しない。

一回制限、介在if、遅延誘発、コピー、追加誘発、置換、複雑な条件の全対応を本書だけで宣言しない。旧対応をケースごとに移植し、成立しないものは理由を示す要確認へ残す。

## 8. 保存・再接続・非公開情報

候補の生成と原因となった盤面変更、候補の登録とスタック追加、候補の除外と記録は各々同じtransactionに含める。receiptの成功前にUIで処理済みにしない。

Undo/Redoは候補と対応関係も盤面と一緒に戻す。Undoは新しい死亡・離場・ドロー等として検出しない。Undoで分岐後の出来事を再利用しない。回数制限の消費と候補除外も復元対象として扱う。

再接続・複数タブ・WebSocket更新・同じrequestIdの再送で再検出しない。旧保存には空の新記録を補完し、ロード時に既にある盤面から過去の誘発を捏造しない。導入前の出来事は遡れない旨を保存復帰時に一度説明する。

検出はサーバーの正本で行い、Feedへの公開は既存audience境界を通す。非公開カードの名前、本文、候補数、ID、警告内容から相手の手札・ライブラリーが漏れないようにする。共有すべき誘発が公開される時点と、秘匿のまま本人だけへ確認させる情報を区別する。ログに生のoperation payloadや秘密識別子を流用しない。

## 10. 実装の順序とレビュー

1. 今回: 旧／現行の差を確認し、本設計とQAを作る。既存の誘発・Feed関連テストを診断として実行する。
2. サーバーの出来事と履歴を、まず代表ETB／ドロー経路へ追加。手動操作を含む発生元、失敗・再送・Undoを検証する。
3. 旧collectorの適用可能な条件を接続。候補の生成・snapshot・保存・投影を実装し、未対応を明示する。
4. 候補登録／手動登録との関連付けを原子的にする。起動と誘発の作業面を整理する。
5. 旧Feedの表示文法を現在の作業面へ接続。主操作・ベル・既読・盤面復帰を整える。
6. 旧対応の残りをイベント種ごとに広げ、QAと対応表を更新。多人数の秘密・権限と保存変更は独立した読み取り専用レビューを受ける。

段階2以降は永続化・共有状態・主要CR意味論へ触れるため、実装レビューを省略しない。旧Feedを先に表示し空の候補で完了とすることや、クライアントの一時候補で正本不足を隠すことはしない。

## 設計QA後に固定した実装契約

### A. 正本と操作内の出来事

保存先はCockpitTableとする。出来事の有界な記録、未処理候補と対応状況、一回制限等の検出に必要なledgerをtableに含め、既存のundo/redo snapshotと同じ単位で戻す。SessionRecordに別の正本を追加しない。旧保存のtableおよび全undo/redo要素をbackfillする。

applyTableOperationの外部返却型はCockpitTableを維持する。内部の意味操作がordered event traceを集め、その操作の確定結果へ格納する。内側の再帰呼び出しを別のユーザー操作として再検出しない。外側の確定操作ID、内部の連番、同時グループを引き継ぐ。検出が必要とする途中のsnapshotをその地点で保持し、最終状態の差分だけに依存しない。純粋関数内で乱数・壁時計によるIDを生成しない。

turn.ready/shortcutは重要な区切りを飛び越さない。upkeep等で登録すべき誘発が生じた場合は、そこで止まった状態をその操作の成功結果として保存する。解決後に残りを進めるための進行地点を保存し、再開時に同じドローやアンタップを繰り返さない。エラーで途中結果を保存するという意味ではない。エラー時は従来どおりtransaction全体を戻す。候補なしの通常キープ→main1経路は維持する。解決の内部では区切りが来るまで誘発を待機させる。

### B. 登録順と操作権

候補に発生時controllerと登録windowを保存する。各windowの登録はCR 603.3bの区分とAPNAP順を扱い、同一controller内の順序と必要な対象・モードを登録下書きで選ぶ。現在のmasterが、各席の判断を会話で確認し操作する経路を維持する。記録のoperatorとtrigger controllerは別項目にする。masterという理由で能力のcontrollerをmasterへ書き換えたり、APNAP順を自由に入れ替えたりはできない。

非masterに新たな誘発登録権限を自動付与しない。今回のQAで提案された「controller本人か席別委任だけが登録可能」という方式は、既存の手動卓の操作権と異なるため採用しない。必要な修正は登録順とcontrollerの検証であり、マスターによる合意済み代行自体の禁止ではない。

### C. 自動検出へ昇格できる条件

各候補にdetectionBasis（使った出来事、snapshot、能力行、対応条件）とrequiresManualRulingを保持する。旧collectorが返したという理由だけで確定候補にしない。次を観測・判定できない場合は要確認へ送り、意味不明の値を補完しない。

- CR603.2fの発生源の公開条件。必要な公開履歴を保持せず、非公開カードの存在だけから誘発を作らない。
- CR603.2gの置換・軽減後に実際に生じた出来事。予定ダメージや単なるライフ調整を確定ダメージとみなさない。
- CR603.4の介在if。発生時の不成立なら誘発せず、成立したものも解決時に再確認する。
- 遅延・反射誘発（603.7/603.12）。作られた条件と時点を保持できないものは、本文のタグだけで確定候補にしない。

これらをQ4/Q6/Q11へ追加したP0のQA条件とする。一般の置換や軽減を今回自動解決する要求へ広げず、手動裁定後の実際の出来事を記録する経路も用意する。

### D. Feed投影

サーバー内部の候補をそのままwireへ直列化しない。席別のTriggerFeedProjectionは、visibleItems（表示ID、kind、公開可能なsourceRef、短い本文、回数、許可された操作）と、その席が見られる未処理件数だけを返す。非公開の出来事のoperation payload・内部ID・snapshot全文は送らない。

各候補のaudienceと公開可能な項目をサーバーが決める。受信権限のない候補は行を丸ごと省略し、伏字の行や全体件数との差から存在を漏らさない。公開が必要な出来事は公開のタイミングを通じて別途適切に見せる。秘密の異なる二状態で公開情報が同じなら、非権限席のFeed行・件数・警告・操作一覧も同じ、という比較をQ11の不変条件にする。表向きになった後の情報利用と、非公開だった過去のLKIを遡って開示することは分ける。

### QAの結論

独立した読み取り専用QAから5件の設計具体化要求を受け、保存位置、途中イベント、登録順、検出根拠、投影の契約を上記へ追記した。登録権限を席ごとに増設する提案のみ、既存のマスター方式に合わせて修正した。実装時にはこの契約に沿った型・transaction・projectionの検証と独立レビューが必要。この時点の成果は設計と事前QAであり、統合実装の完了判定とは分ける。後続の実装結果は次節を参照する。
