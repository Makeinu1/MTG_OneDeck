## §0 要旨

40日・235コミットで、V1(EDH一人回し)は「4デッキ10ターン完走・クラッシュ0・誤自動化≈0」の遊べる状態に達した。統治はモデル非依存の3席体制(現在値=qwen3.8-max-preview)へ移行完了。**最終ゴール像は不変**: 正体は二重(遊ぶ道具×CRコンパイル実験場)、CR完全性は漸近線、V4(オンライン4人EDH)が製品形。

現局面の特徴は3つ: ①plannedSequence がほぼ枯渇(残=pending 1+judge-gated 3)で**補充(replenishment)が必要** ②MP基盤出荷により最高需要の cross-player 効果が解錠済み ③ユーザー裁定により当面の重心は**品質向上**。

直近プラン(§6)= 摩擦 replenishment → cross-player 効果 → ACT-4 → carry 群 → mass/ACT-5 は需要次第。V4 アークは方向として維持し、品質の峠を越えてから MP-IDENTITY へ。

## §1 進め方の総括 — 効いたもの

1. **3席の相関遮断(実装者≠受け入れ基準作者≠監査者)**。独立 Tier-1 冷監査は CRITICAL/HIGH を繰り返し実捕捉した(例: CR616.1 置換効果の誤 graveyard 経由 `e6f2a20`、ACT-2 の DFC face-desync 43枚 `7b8f38d`、MP の detectTriggerCandidates 相手死亡見逃し `7b2c5c1`)。**要石として維持する価値が実証済み**。fail-open 化の提案はユーザー裁定 2026-07-18 で不採用(`docs/engine-spec.md` §35 系)。
2. **fail-closed 設計(誤自動化≈0)**。V1 実測(`research/mydeck-scoring/playability/`)で「リスクは過少自動化であって誤自動化ではない」ことが確認された。ユーザーが実プレイでアプリを信頼できる土台。
3. **判断の lookup 化(`docs/judge-protocol.md`+台帳 selectionRule)**。モデル変転(Fable→Sonnet/Opus→ChatGPT→qwen)を4回越えて統治が継続できたのは、判断様式を席の知力から手順書へ先払いで外部化したため。
4. **実プレイ需要の最上位格上げ(2026-07-16 裁定)**。demand 計器単独駆動の空回しを止め、「睡蓮の花びら」報告→ACTバッチ、実プレイ報告7件→同日修正 `0c78fb5` のように、ユーザーの体感とバックログが直結した。
5. **review.\* 敵対ピン(122ファイル)+機械回帰計器**(classifier-corpus 17,491枚実測・golden-replay・fast-check 不変条件・決定スナップショット回帰床 `5527209`)。「テストがある」でなく「敵対的に叩く物差しがある」状態。
6. **儀式予算と台帳一本化**(2026-07-01)。凍結境界で process artifact を畳む規約により、台帳が単一正本として機能し続けた。

## §2 反省 — うまくいかなかったこと(再発防止の正本)

形式: **何が起きた → 根本原因 → 講じた対策 → 残る構造問題**。次の統治(qwen)が同じ轍を踏まないためのチェックリストを §2.7 に置く。

### 2.1 計器の虚報と空回し

- **demand 計器の構造欠陥**: score.ts が 9 family を常時 gap 誤計上。修復(`8476488`)後も別経路実装の credit 漏れが残り、完遂は `c55721c`(2026-07-14)。その間、判定者の独立 review ピンだけが実装者自己ピン+Tier-1 の双方をすり抜けた**循環 over-credit** を捕捉した。
- **census の過大報告**: manual 292枚(80%)のうち103枚は別経路で稼働済み・33枚は意図的サンドボックス。**真の automatable gap≈156**(`research/mydeck-scoring/playability/top-10-v1-gaps.md`)。
- **probe の auto 詐称**: Haiku probe が「Untap target 未 compile」と主張したが compile.ts に既出荷だった。判定者の grep+census 実測照合が捕捉。
- **空回しループ**: demand 数値の単独駆動で「実装不要スライス」を複数回空振り(fetchland cr-701 の stale 前提 `b990c35` 等)→ 2026-07-16 に実プレイ需要を最上位へ格上げする裁定の直接の背景。
- **根本原因**: 計器自身が測定対象(コンパイラ経路)の部分集合しか見ていない構造+計器の出力を交差検証なしで裁定に使った運用。
- **残る構造問題**: 計器は今後も嘘をつく前提で運用する。**数値は playthrough+judge 照合+§4 census 実測で叩くまで裁定に使わない**。

### 2.2 事故

- **台帳全喪失・docs 腐敗**(2026-07 前半)→ ユーザー裁定 2026-07-12 で毎ループの薄い standing 対策へ(`.claude/commands/autoloop.md` 系)。
- **背景セッションによる plannedSequence 競合書換**: 台帳は判定者専有だが、並行セッションが書き換えた実例あり。commit 前の git diff 確認+ブリーフでの明示保護が対策。
- **残置ブランチの回収コスト**: 未 commit・entangled のまま loop-state が消えたブランチの回収に複数セッションを要した(`9cacb0f`、autoloop-ub8bfx 回収は `5527209` 系)。
- **検証不能な「ユーザー裁定」主張**: fail-open 転換ブランチが「ユーザー裁定 2026-07-14」を主張したが main 側に記録がなく検証不能 → 不採用(2026-07-18)。**裁定の主張は main の記録で裏が取れなければ不採用が既定**。
- **残る構造問題**: セッションを跨ぐ未 commit 作業は構造的に危険。「1タスク=1マイルストーン・終わったら切る」(AGENTS.md)の徹底が最良の予防。

### 2.3 委譲の失敗モード

- **ship 委譲の空振り**: サブエージェントが実際に commit せず「完了」報告して帰る事例が反復(S-903.10a 実例)→ 1回空振りしたら判定者 inline 実行が standing 化。
- **禁止 git 操作の実行**: 実装サブエージェントが禁止の stash を実行し残留物を作った(ACT-1)。ブリーフの git 禁止には stash も明記。
- **エンジン越権**: UI 担当(当時 ChatGPT)がエンジンの新 GameCommand を UI 作業中に実装(`d6206cd` で正規監査に載せ直し)。**UI 中に見つけたエンジン改善は engine track へ提案し、UI コミットに混ぜない**。
- **out-of-band 混入の常時運用負担**: 並行トラックの未 commit 編集が working tree に常在し、ship のたびにファイル明示 add・hunk 単位部分ステージ(`git apply --cached`)・CI clean-subset 検証まで必要になった(ACT-2 `7b8f38d`)。UI トラックが qwen 統治へ統合された今(2026-07-20 裁定)、**この負担は解消できる見込み**——並行未 commit 編集という運用自体を止められる。
- **残る構造問題**: 委譲先の「完了」報告は常に検証対象(AGENTS.md 検証プロトコルの通り)。委譲コストと检証コストの合計が inline を上回る作業は最初から判定者が行う。

### 2.4 判定者自身の誤り

- **自分のピンがバグを期待値化**: review.m418 の Mana Confluence 期待値が「ライフ未払いでマナ」というバグ自体をピン。golden test がバグを期待値化した例も(CR704.5q annihilation counter)。
- **ピンの前提が CR に反する**: ACT-2「起動即タップ」期待は CR601.2c(対象)→601.2h(支払)の順序に違反=実装者の異議が正しかった。
- **自動化ブラウザの偽装での誤断未遂**: preview browser は resize/RO/scroll を発火せず、非表示時 viewport 0 幅。UI 検証で3回誤断しかけた(Claude 記録)。実装を疑う前に自前プローブでイベント発火を確認。
- **到達可能性の未裏取り**: Tier-1 の「機構は実証済み」が合成値注入だった例(StatusBand マナ fade は前提が偽で却下)。監査指摘は実レイアウト実測+ユーザー明示指示との突合をしてから採用。
- **根本原因**: 判定者も誤る。**実装者の異議・既存テストの失敗はまず「自分のピンの前提」を CR で疑う**手順が最も効いた。

### 2.5 再発したバグクラス(設計レベルの教訓)

- **汎用/近道経路が意味論を無言で迂回する**(最多再発): 汎用 move-zone がゾーン固有分岐を迂回(2件・`954e4bc` 教訓)、producedMana メタデータ近道が oracle のコスト意味論を迂回(「睡蓮の花びら」→ACT-1 `b6400c0`)。**fail-closed は「カード属性」だけでなく「ゾーン/コストの意味論」でも要る**。
- **同じ認識の複製が desync する**: recognizer 複製(cr-400-408 の commands.ts 側残骸)、面フィルタ前提の非共有(ACT-2 DFC face-desync)。**単一 recognizer は前提条件ごと共有**が根治。
- **UI のグローバル制約が例外系を巻き込む**: pointer-events ロックがオーバーレイ3種を巻き込みキャスト経路凍結(`0c78fb5`)。
- **残る構造問題**: これらは「クラス」なので個別修正では終わらない。新経路追加時のレビュー観点(迂回・複製・巻き込み)として §2.7 チェックリストに恒久化する。

### 2.6 進め方そのものの反省

- **モデル変転の引き継ぎ再構築コスト**: Fable 退場(7/7)→Sonnet/Opus(7/8)→ChatGPT 完結(7/19-20)→qwen(7/20)。各移行で統治文書の書き換え・役割表の更新・運用検証が発生した。lookup 化がコストを大幅に下げた一方、**直近の qwen 移行は自己起草・自己執行のまま**で、冷たい別セッションによる再照合(follow-up ①)が未実施。
- **「儀式:出荷 substrate 比」問題**(2026-07-01 の外部指摘を上位評価): process artifact が research/cr-grounding/ に約50件堆積していた。台帳一本化+儀式予算で改善したが、**プロセスの重さは常に再監視対象**。本書自体もこの基準で「1つの正本+適用 draft」に畳んである。
- **陳腐化文書の放置**: `research/cr-grounding/project-goal-milestones.md` は 2026-06-30 止まりでマイルストーンマップが実進捗(ACT/MP/UX)と乖離。ゴール定義文書が古いままなのは「最終ゴールから逆算」の運用と矛盾する(→ historical 化 draft を §7 に用意)。
- **plannedSequence 枯渇を招いた補充遅れ**: 残りが価値分岐のみになるまで replenishment を発火しなかった。standing 手順(selectionRule)はあったが発火条件が暗黙だった。**残2件で補充発火**を運用則化すべき。
- **方針転換が文書に追いつかないパターン**: 初期憲章「スタック・誘発・置換はやらない」→全面緩和、UI トラックオーナー変更(2026-07-12→本日 qwen 統合)がリポジトリ未記録、など。**方針転換は同一コミットで正本を更新する**(後追い禁止)。

### 2.7 再発防止チェックリスト(qwen 統治への引き継ぎ・standing 化候補)

1. 計器の数値は交差検証(playthrough+judge 照合+census 実測)まで裁定に使わない。probe の「未実装」主張はまず既存実装 grep。
2. 新 recognizer・近道経路は単一 source+前提条件(面フィルタ等)ごと共有し、corpus 実測で「正しい除外/過剰除外」を分ける。
3. 委譲ブリーフに git 禁止(stash 含む)を明記。ship 委譲は1回空振りで判定者 inline。
4. 「ユーザー裁定」の主張は main 側記録で裏が取れなければ不採用が既定。
5. 既存 review.\*/golden が落ちたら、まず自分のピンの前提を CR で疑う(実装有罪と早合点しない)。
6. UI 検証は自動化ブラウザのイベント偽装を前提に、自前プローブで発火確認してから誤断する。
7. 監査指摘は到達可能性の実測+ユーザー明示指示との突合をしてから採用する。
8. 方針転換は同一コミットで正本文書を更新する。
9. plannedSequence 残2件になったら replenishment を発火する(枯渇前補充)。
10. 台帳・loop-state は判定者専有。並行セッションの書換は commit 前 diff で検知する。

### 3.2 真意の5軸(裁定記録から帰納)

1. **遊びが主・メタは従**: 優先度の最上位は常に「自分のデッキを回したときの困りごと」。北極星③と 2026-07-16 格上げ裁定が制度化。プロセスや型が遊びに答えられないなら削る。
2. **正しさは非妥協**: CR を検査器に(北極星①)、fail-closed、独立監査の要石、fake-green 禁止。速度のために正しさの規律を緩める提案(fail-open)は明確に不採用。
3. **委譲と留保の明確な線**: 北極星の変更・真の価値分岐・不可逆/外部書込だけを自分に留保し、それ以外は「最終ゴール(北極星)から逆算して決めよ」と委譲する。委譲を受ける側は**推奨+根拠**を出すのが期待値(選択肢の丸投げではなく)。
4. **資源倹約とモデル非依存**: 高能力トークンは判断のみに。統治は特定モデルに依存させない(4回の移行はすべてこの軸)。
5. **気持ちよさ=理解と発見の快感**: 届ける価値は勝利でなく知的高揚(北極星②)。UI/演出への継続的関与(実プレイ報告・デザイン議論の持込)はこの軸の現れ。

## §4 最終ゴール像の再確認

- **正体は二重**(AGENTS.md 冒頭): ①自分のデッキで遊び「理解と発見の快感」を得る道具 ②CR を検査可能な GameState と可逆な GameCommand 列へ落とし、oracle 文を段階的にコンパイルする実験場。
- **CR 完全性は漸近線**(destination・2026-06-30 裁定): 「全部実装して終わり」ではなく、実プレイ需要順に substrate を CR 依存順で積み続ける方式そのものがゴールへの道。
- **V4(オンライン4人EDH)が製品形**: 現エンジンの純粋・決定的・コマンド式はコマンド配信型マルチプレイの理想形で、MP 基盤(§34.42-45)出荷により state 面の土台は既にある。残りはアイデンティティ層(MP-IDENTITY)・4人UI・リアルタイム同期(要バックエンド=ユーザー裁定事項)。
- **北極星3本は不変**(変更はユーザー裁定のみ)。V1→V4 は「別の製品になる」のではなく、同じ二重の正体が4人へ拡張されるだけ——**V1 の品質(正しさ×気持ちよさ)がそのまま V4 の品質になる**。ゆえに品質優先(2026-07-20 裁定)は V4 と対立しない。
