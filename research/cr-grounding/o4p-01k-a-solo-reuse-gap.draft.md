## Report: evidence, regressions, and DEFERs

### Evidence and path

The inspected implementation paths are `src/engine/priority.ts`, `src/engine/triggers.ts`, `src/engine/commands.ts`, `src/engine/types.ts`, and `src/store/gameStore.ts`. The strongest existing evidence is:

- `priority.ts:66-197` implements APNAP rotation, bucket normalization, explicit-order validation, and deterministic singleton grouping.
- `priority.ts:288-393` implements the current SBA → pending-choice → pending-trigger placement → repeat boundary, but only over the currently implemented Solo SBA/trigger catalog and with a bounded iteration fallback.
- `types.ts:552-640` contains the pending-trigger and rule-choice payloads; `types.ts:676-714` shows lifecycle fields plus legacy duplicate state in one mutable `GameState`.
- `types.ts:803-897` derives/repairs players and turn order from legacy scalar views, demonstrating compatibility behavior rather than a Core alias contract.
- `review.mp-state.test.ts` provides the clearest multi-player evidence for roster/turn order, active-player/APNAP input, and legacy snapshot repair. `priority.test.ts`, `planCleanup.test.ts`, `delayedTriggers.test.ts`, and the CR 603 review tests provide focused trigger, ordering, delayed-trigger, cleanup-choice, and boundary evidence.
- Core identity-zone tests validate seated active player, unique ordered players, player-set agreement, canonical fresh output, and deep-freeze behavior. Core stack transaction tests cover structural stack transactions, not lifecycle authority, phase, priority, SBA, or resolution.

### Regression risks

1. Reading Solo duplicates instead of Core identity would make APNAP and active-player rotation non-deterministic after restore or multiplayer expansion.
2. Treating `priority-ready` as resolved would skip the stack/effect-resolution boundary explicitly deferred by O4P-01K.
3. Flattening phase into `Phase` or treating `combat` as a complete step would violate no-priority untap and cleanup-repeat behavior under CR 500.2–500.6, 502.4, and 514.
4. Reusing regex trigger detection as a Core semantic would turn current card-parser limitations into a mode-neutral false authority; this is why the matrix classifies it `SOLO_ONLY`.
5. Copying mutable Solo payloads into Core would violate Core’s validated, canonical, deeply frozen representation and could expose stale source snapshots, hidden zones, Japanese UI text, or client-owned choices.

### Explicit DEFERs

- Concrete SBA catalog completion, trigger detection completeness, target legality, full spell/ability resolution, combat, control/permission, command/event envelope, replay, Online, Cloudflare, and UI remain outside O4P-01K as stated by the orchestration plan.
- Additional turns/phases, skipped/inserted steps, effect expiration, priority legality, mana abilities, and all card-specific turn-based actions require a lifecycle contract or later CR-ordered milestone; they are not implied by `PHASE_ORDER`.
- No claim is made that Solo types can alias or extend Core types. Reuse requires explicit validated adapters and separate contracts for lifecycle, choices, triggers, and projections.
