# CR 604/611/612/613 Layers Continuous Effects Batch3-5 Draft

Status: design draft only. No production implementation in this file.

Source authority: `rule/Magic_The_Gathering_Comprehensive_Rules.txt`, pinned 2026-06-19.

## CR Grounding

### Static abilities and characteristic-defining abilities

> 604.1. Static abilities do something all the time rather than being activated or triggered. They are written as statements, and they’re simply true.

> 604.2. Static abilities create continuous effects, some of which are prevention effects or replacement effects. These effects are active as long as the permanent with the ability remains on the battlefield and has the ability, or as long as the object with the ability remains in the appropriate zone, as described in rule 113.6.

> 604.3. Some static abilities are characteristic-defining abilities. A characteristic-defining ability conveys information about an object’s characteristics that would normally be found elsewhere on that object (such as in its mana cost, type line, or power/toughness box). Characteristic-defining abilities can add to or override information found elsewhere on that object. Characteristic-defining abilities function in all zones. They also function outside the game and before the game begins.

> 604.3a A static ability is a characteristic-defining ability if it meets the following criteria: (1) It defines an object’s colors, subtypes, power, or toughness; (2) it is printed on the card it affects, it was granted to the token it affects by the effect that created the token, or it was acquired by the object it affects as the result of a copy effect or text-changing effect; (3) it does not directly affect the characteristics of any other objects; (4) it is not an ability that an object grants to itself; and (5) it does not set the values of such characteristics only if certain conditions are met.

> 604.4. Many Auras, Equipment, and Fortifications have static abilities that modify the object they’re attached to, but those abilities don’t target that object. If an Aura, Equipment, or Fortification is moved to a different object, the ability stops applying to the original object and starts modifying the new one.

Implication: an unconditional self subtype-defining line such as "This creature is [subtype] in addition to its other types" may be a CDA under 604.3a and therefore functions in all zones. A battlefield-only first slice should either exclude CDAs or explicitly accept that it is not a full CR implementation for such lines. Aura/Equipment effects that modify the attached object are not CDAs because they affect another object.

### Continuous-effect sources and duration

> 611.1. A continuous effect modifies characteristics of objects, modifies control of objects, or affects players or the rules of the game, for a fixed or indefinite period.

> 611.2. A continuous effect may be generated by the resolution of a spell or ability.

> 611.2a A continuous effect generated by the resolution of a spell or ability lasts as long as stated by the spell or ability creating it (such as “until end of turn”). If no duration is stated, it lasts until the end of the game.

> 611.2b Some continuous effects generated by the resolution of a spell or ability have durations worded “for as long as . . . .” If the “for as long as” duration never starts, the effect does nothing. Similarly, if that duration ends before the moment the effect would first be applied and doesn’t begin again during that spell or ability’s resolution, the effect does nothing. It doesn’t start and immediately stop again, and it doesn’t last forever.

> 611.2c If a continuous effect generated by the resolution of a spell or ability modifies the characteristics or changes the controller of any objects, the set of objects it affects is determined when that continuous effect begins. After that point, the set won’t change. (Note that this works differently than a continuous effect from a static ability.) A continuous effect generated by the resolution of a spell or ability that doesn’t modify the characteristics or change the controller of any objects modifies the rules of the game, so it can affect objects that weren’t affected when that continuous effect began. If a single continuous effect has parts that modify the characteristics or changes the controller of any objects and other parts that don’t, the set of objects each part applies to is determined independently.

> 611.2d If a resolving spell or ability that creates a continuous effect contains a variable such as X, the value of that variable is determined only once, on resolution. See rule 608.2h.

> 611.2e If a resolving spell or ability both puts a nontoken permanent onto the battlefield and creates a continuous effect stating that the permanent “is [characteristic],” that it “has [characteristic],” or that it doesn’t have a particular characteristic, that continuous effect applies simultaneously with the permanent entering the battlefield. This characteristic is usually a color or a creature type. If the continuous effect says the permanent “becomes [characteristic]” or “gains [an ability],” that effect applies after the permanent is on the battlefield.

> 611.3. A continuous effect may be generated by the static ability of an object.

> 611.3a A continuous effect generated by a static ability isn’t “locked in”; it applies at any given moment to whatever its text indicates.

> 611.3b The effect applies at all times that the permanent generating it is on the battlefield or the object generating it is in the appropriate zone.

> 611.3c Continuous effects that modify characteristics of permanents do so simultaneously with the permanent entering the battlefield. They don’t wait until the permanent is on the battlefield and then change it. Because such effects apply as the permanent enters the battlefield, they are applied before determining whether the permanent will cause an ability to trigger when it enters the battlefield.

Implication: this first slice should not start with 611.2 generated-by-resolution effects. Those require duration records, object-set locking, variable capture, and sometimes simultaneous ETB application. Static abilities under 611.3 are a better first target because their current applicability can be derived from current `GameState`.

### Text-changing distinction

> 612.1. Some continuous effects change an object’s text. This can apply to any words or symbols printed on that object, but generally affects only that object’s rules text (which appears in its text box) and/or the text that appears in its type line. Such an effect is a text-changing effect.

> 612.3. Effects that add or remove abilities don’t change the text of the objects they affect, so any abilities that are granted to an object can’t be modified by text-changing effects that affect that object.

Implication: "has flying" / "gains flying" is Layer 6 ability addition, not text-changing. Text-changing Layer 3 remains out of scope for the first slice.

### Layer list and order

> 613.1. The values of an object’s characteristics are determined by starting with the actual object. For a card, that means the values of the characteristics printed on that card. For a token or a copy of a spell or card, that means the values of the characteristics defined by the effect that created it. Then all applicable continuous effects are applied in a series of layers in the following order:

> 613.1a Layer 1: Rules and effects that modify copiable values are applied.

> 613.1b Layer 2: Control-changing effects are applied.

> 613.1c Layer 3: Text-changing effects are applied. See rule 612, “Text-Changing Effects.”

> 613.1d Layer 4: Type-changing effects are applied. These include effects that change an object’s card type, subtype, and/or supertype.

> 613.1e Layer 5: Color-changing effects are applied.

> 613.1f Layer 6: Ability-adding effects, keyword counters, ability-removing effects, and effects that say an object can’t have an ability are applied.

> 613.1g Layer 7: Power- and/or toughness-changing effects are applied.

Layer order is the CR model even for one effect. For a single additive Layer 4 type-add effect on one object, order is not observable unless another continuous effect interacts with the result. That means Slice A can be honest about being "Layer 4-tagged effective type calculation" without building timestamp/dependency machinery yet.

### Layer 1, including L1b

> 613.2. Within layer 1, apply effects in a series of sublayers in the order described below. Within each sublayer, apply effects in timestamp order (see rule 613.7). Note that dependency may alter the order in which effects are applied within a sublayer. (See rule 613.8.)

> 613.2a Layer 1a: Copiable effects are applied. This includes copy effects (see rule 707, “Copying Objects”) and changes to an object’s characteristics determined by merging an object with a permanent (see rule 730, “Merging with Permanents”). “As . . . enters” and “as . . . is turned face up” abilities generate copiable effects if they set power and toughness, even if they also define other characteristics.

> 613.2b Layer 1b: Face-down spells and permanents have their characteristics modified as defined in rule 708.2.

> 613.2c After all rules and effects in layer 1 have been applied, the object’s characteristics are its copiable values. (See rule 707.2.)

The ledger demand includes `layer:L1b=1`, but face-down characteristics are not a good first-slice partner for L4/L6 static effects. This draft recommends deferring L1b.

### Within layers 2-6

> 613.3. Within layers 2–6, apply effects from characteristic-defining abilities first (see rule 604.3), then all other effects in timestamp order (see rule 613.7). Note that dependency may alter the order in which effects are applied within a layer. (See rule 613.8.)

Layer 4 and Layer 6 both use this rule. Slice A can avoid observable timestamp/dependency by supporting only additive, non-removing, non-replacing effects whose order is commutative, and by excluding CDAs unless the judge chooses all-zone CDA work.

### Counters and power/toughness

> 613.4. Within layer 7, apply effects in a series of sublayers in the order described below. Within each sublayer, apply effects in timestamp order. (See rule 613.7.) Note that dependency may alter the order in which effects are applied within a sublayer. (See rule 613.8.)

> 613.4c Layer 7c: Effects and counters that modify power and/or toughness (but don’t set power and/or toughness to a specific number or value) are applied.

> 122.1. A counter is a marker placed on an object or player that modifies its characteristics and/or interacts with a rule, ability, or effect. Counters are not objects and have no characteristics. Notably, a counter is not a token, and a token is not a counter. Counters with the same name or description are interchangeable.

> 122.1a A +X/+Y counter on a creature or on a creature card in a zone other than the battlefield, where X and Y are numbers, adds X to that object’s power and Y to that object’s toughness. Similarly, -X/-Y counters subtract from power and toughness. See rule 613.4c.

> 122.1b A keyword counter on a permanent or on a card in a zone other than the battlefield causes that object to gain that keyword. The keywords that a keyword counter can be are flying, first strike, double strike, deathtouch, decayed, exalted, haste, hexproof, indestructible, lifelink, menace, reach, shadow, trample, and vigilance, as well as any variants of those keywords. See rule 613.1f.

Current engine support for +1/+1 and -1/-1 counters is related to CR 613.4c, but it is ad hoc P/T computation, not a general layer engine. Keyword counters are Layer 6 under 122.1b/613.1f, but this repo does not currently model keyword counters as automatic ability grants.

### Continuous automatic application

> 613.5. The application of continuous effects as described by the layer system is continually and automatically performed by the game. All resulting changes to an object’s characteristics are instantaneous.

Read-time derivation matches this better than writing one-time mutations onto `CardInstance.typeLine` because the result is continuously recomputed from current source/attachment state.

### Multi-layer effects

> 613.6. If an effect should be applied in different layers and/or sublayers, the parts of the effect each apply in their appropriate ones. If an effect starts to apply in one layer and/or sublayer, it will continue to be applied to the same set of objects in each other applicable layer and/or sublayer, even if the ability generating the effect is removed during this process.

This is a reason to defer broad effects such as "is a Wizard and has [ability]" or "becomes a creature with base power/toughness" if the implementation cannot represent the same object-set across multiple layers. A narrow additive L4-only slice avoids this.

### Timestamp and dependency

> 613.7. Within a layer or sublayer, determining which order effects are applied in is usually done using a timestamp system. An effect with an earlier timestamp is applied before an effect with a later timestamp.

> 613.7a A continuous effect generated by a static ability has the same timestamp as the object the static ability is on, or the timestamp of the effect that created the ability, whichever is later. If the effect that created the ability has the later timestamp and the object the ability is on receives a new timestamp, each continuous effect generated by static abilities of that object receives a new timestamp as well, but the relative order of those timestamps remains the same.

> 613.7b A continuous effect generated by the resolution of a spell or ability receives a timestamp at the time it’s created.

> 613.7c Each counter receives a timestamp as it’s put on an object or player. If that object or player already has a counter of that kind on it, each counter of that kind receives a new timestamp identical to that of the new counter.

> 613.7d An object receives a timestamp at the time it enters a zone.

> 613.7e An Aura, Equipment, or Fortification receives a new timestamp each time it becomes attached to an object or player.

> 613.7m If two or more objects would receive a timestamp simultaneously, such as by entering a zone simultaneously or becoming attached simultaneously, their relative timestamps are determined in APNAP order (see rule 101.4). Objects controlled by the active player (or owned by the active player, if they have no controller) have an earlier relative timestamp in the order of that player’s choice, followed by each other player in turn order.

> 613.7n If a continuous effect generated by a static ability of an object and a continuous effect generated by a resolving spell or ability that applies to that object would receive a timestamp simultaneously, such as due to an effect that puts that object onto the battlefield and sets its characteristics (see rule 611.2e), the continuous effect from the object’s own static ability receives an earlier relative timestamp.

> 613.8. Within a layer or sublayer, determining which order effects are applied in is sometimes done using a dependency system. If a dependency exists, it will override the timestamp system.

> 613.8a An effect is said to “depend on” another if (a) it’s applied in the same layer (and, if applicable, sublayer) as the other effect; (b) applying the other would change the text or the existence of the first effect, what it applies to, or what it does to any of the things it applies to; and (c) neither effect is from a characteristic-defining ability or both effects are from characteristic-defining abilities. Otherwise, the effect is considered to be independent of the other effect.

> 613.8b An effect dependent on one or more other effects waits to apply until just after all of those effects have been applied. If multiple dependent effects would apply simultaneously in this way, they’re applied in timestamp order relative to each other. If several dependent effects form a dependency loop, then this rule is ignored and the effects in the dependency loop are applied in timestamp order.

> 613.8c After each effect is applied, the order of remaining effects is reevaluated and may change if an effect that has not yet been applied becomes dependent on or independent of one or more other effects that have not yet been applied.

Timestamp/dependency are real requirements for a full Layer 4/6 engine. They can be deferred only if Slice A explicitly supports additive effects with no replacement/removal conflict and no effect whose applicability changes based on another supported same-layer effect.

### Override, player effects, and rule effects

> 613.9. One continuous effect can override another. Sometimes the results of one effect determine whether another effect applies or what another effect does.

> 613.10. Some continuous effects affect players rather than objects. For example, an effect might give a player protection from red. All such effects are applied in timestamp order after the determination of objects’ characteristics. See also the rules for timestamp order and dependency (rules 613.7 and 613.8).

> 613.11. Some continuous effects affect game rules rather than objects. For example, effects may modify a player’s maximum hand size, or say that a creature must attack this turn if able. These effects are applied after all other continuous effects have been applied. Continuous effects that affect the costs of spells or abilities are applied according to the order specified in rule 601.2f. All other such effects are applied in timestamp order. See also the rules for timestamp order and dependency (rules 613.7 and 613.8).

These are out of scope for Slice A.

## Existing-Pattern Survey

### Card instance storage

`src/engine/types.ts` stores `CardInstance` as object identity and mutable game status: `defId`, `zone`, `ownerId`, `controllerId`, `zoneChangeCounter`, tapped/face fields, `counters`, `damageMarked`, `hasDeathtouchDamage`, `manualKeywords`, `attachedTo`, and stack ability metadata. It does not store `typeLine`, `power`, `toughness`, active static abilities, active continuous effects, layer effects, timestamps, or dependencies.

`src/types/card.ts` stores intrinsic card definition data: `CardDef.typeLine`, per-face `CardFace.typeLine`, oracle text, printed text, image, and printed P/T/loyalty. This is the printed/static card definition, not an effective-characteristics record.

`ObjectSnapshot` stores a `typeLine`, `power`, and `toughness`, but existing snapshot creation copies the current face/definition fields. It is not a full effective-characteristics snapshot.

### No production layer system

The production engine has no `computeEffectiveCharacteristics`, `effectiveCharacteristics`, `layerEffect`, or `ContinuousEffect` implementation. The layer-related code found in this survey is research tooling:

- `scripts/lib/layerClassify.ts`: probes oracle text and reports conceptual L1/L4/L6/etc. tags.
- `scripts/lib/oracleHarness.ts`: maps LLM-style facts to layer ids via `factsToLayers`.

Those scripts are informative for test selection/classification only. They are not wired into `GameState`, `applyCommand`, target legality, rendering, or combat.

### Type-line reads are scattered

There is no single exported type-line chokepoint today.

- `src/engine/commands.ts` has private `typeLineOf(draft, card)` and uses it in many runtime paths: battlefield entry effects, legend rule, damage restrictions, SBA, casting destination, and combat creature checks.
- `src/engine/commands.ts` also has `typeLineForStateCard(state, card)` for stack target filtering, but the graveyard and battlefield branches of `eligibleTargets` read `face?.typeLine ?? def?.typeLine` directly.
- `src/engine/status.ts` has private `currentTypeLine(def, card)` and uses it in `isSummoningSick`; it also exports `effectivePower` and `effectiveKeywords`.
- `src/engine/autotap.ts` has its own `currentTypeLine` for source priority.
- `src/engine/triggers.ts` snapshots current printed type lines into event snapshots, and trigger matching uses the snapshot `typeLine`.
- `src/store/gameStore.ts` has local helpers such as `sourceTypeLineFor` and `cardTypeLinesForState`, reading printed/current face type lines.
- UI code reads type lines directly in `src/components/playmat/Battlefield.tsx`, `src/components/playmat/Playmat.tsx`, `src/components/playmat/dialogs.tsx`, `src/components/CardView.tsx`, and `src/components/CardPreview.tsx`.

Blast-radius consequence: adding an `effectiveTypeLine(state, cardId)` function is not enough by itself. The implementation slice must name which read sites are migrated. If only engine SBA/combat uses it, UI grouping, context menus, target pickers, and trigger snapshots may still behave as though the printed type line is authoritative.

### P/T counters and keyword state

Current +1/+1/-1/-1 support is already a partial effective P/T computation:

- `src/engine/status.ts` exports `effectivePower(state, cardId)` using printed base power plus `+1/+1` minus `-1/-1` counters.
- `src/engine/commands.ts` has private `effectiveToughnessForSba(draft, card)` for zero toughness/lethal damage/deathtouch SBA.

This aligns with CR 122.1a and 613.4c for counters, but it is not generalized Layer 7. It does not include 7b base-setting effects, 7d switching, static P/T buffs, or timestamp/dependency.

Keyword support exists but is not Layer 6:

- `src/engine/status.ts` exports `effectiveKeywords(state, cardId)`, currently `possessedKeywords(def)` plus `card.manualKeywords`.
- `possessedKeywords(def)` recognizes printed pure keyword paragraphs, not static grants from another object such as "Equipped creature has flying."
- `manualKeywords` is player-controlled state, not a CR continuous effect.
- CR 122.1b keyword counters are not represented as automatic Layer 6 grants.

### Static ability detection and compile/runtime handling

`src/engine/grammar/index.ts` defines `AbilityShape = 'activated' | 'triggered' | 'delayed-triggered' | 'replacement' | 'static' | 'spell' | 'keyword'`. `classifyAbilityShape` returns `static` as the fallback for non-instant/sorcery lines that are not activated, triggered, delayed-triggered, replacement, spell, or pure keyword.

`src/engine/grammar/ir.ts` preserves `shape` and treats a static line's full text as the effect span. Atom detection can tag `effect.grant-keyword`, `effect.gain-control`, `effect.pump`, etc.

Production compile/runtime does not currently execute static continuous effects:

- `effectLinesForStackItemState` in `src/engine/commands.ts` filters resolved non-ability stack items to `line.shape === 'spell'`.
- Activation helpers require `line.shape === 'activated'`.
- `compileEffect` in `src/engine/grammar/compile.ts` has no special case for `effect.grant-keyword` or `effect.gain-control`; unsupported atoms fall through to manual/needs-parse paths.

Layer 2 note: `CardInstance.controllerId` exists and is used for ownership/controller-aware logic, but the `effect.gain-control` atom is only classification metadata today. There is no general control-changing continuous-effect substrate.

### Derived-cache pattern

`zonesByPlayer` is a derived-and-synced cache: `syncP1ZonesByPlayerFromFlatZones` rebuilds P1 private-zone mirrors from flat zones, and `restoreGame` backfills/normalizes missing fields. A stored `activeContinuousEffects` ledger would become another restore/backfill obligation. A read-time effective characteristic query avoids adding snapshot schema surface for Slice A.

## Feasibility Analysis

### What is genuinely boundable first

The lowest-risk first slice is not a full CR 613 engine. It is a read-time effective type query for a narrow subset of static abilities:

Slice A candidate:

- Additive Layer 4 only.
- Source is a face-up permanent currently on the battlefield.
- Source effect is generated by a printed static ability on that source.
- Affected object is either the source itself or the single object currently referenced by `source.attachedTo`.
- Text patterns are explicitly additive: "in addition to its other types" / "every basic land type in addition to its other types."
- No type removal, no "isn't", no "becomes [type]" without "in addition", no copy/text/control/color/P/T effects.
- No stored GameState field and no GameCommand mutation.

This can produce `effectiveTypeLine(state, cardId)` or a narrower internal equivalent. It should start from the current printed face type line, then append supported additive card type/subtype/supertype words from supported static effects. It should be deterministic and idempotent.

The attachment half is still bounded because `attachedTo` is a single id and existing UI already renders attachments under the attached permanent. It is more work than self-only because the query must inspect other battlefield permanents whose `attachedTo === cardId`, but it is still not an anthem/multi-object effect.

### Does Slice A need real layer ordering?

CR 613.1 requires that continuous effects are applied by layer, and additive type changes are Layer 4 under 613.1d. However, if Slice A supports only additive L4 effects and no interacting L1/L2/L3/L5/L6/L7 effects, timestamp and dependency cannot change the result. Multiple additive subtype additions are commutative; "Land + Mountain + Wizard" yields the same type words regardless of order.

Therefore Slice A should carry a layer tag internally or in tests for future expansion, but it does not need a dependency graph, timestamp sorting, or a general `ContinuousEffect` ledger yet. Building those now would be architecture for unsupported behavior rather than a bounded first slice.

### Read-time query vs stored effect ledger

Recommended for Slice A: pure read-time computation.

Pros:

- Matches 611.3a: static effects are not locked in and apply to whatever the text indicates right now.
- Matches 613.5: effective characteristics are continuously and automatically derived.
- Keeps `GameState` minimal and avoids restore/backfill/schema churn.
- Keeps undo/reversal simple because no command writes effective type data.
- Makes attachment changes naturally reversible: changing `attachedTo` changes the derived result.

Cons:

- Scattered read sites must be migrated deliberately.
- Recomputing by scanning battlefield/attachments may need memoization later, though current board sizes are small.
- It cannot represent 611.2 resolution-generated continuous effects, object-set locking, variable capture, "until end of turn", or timestamp conflicts.
- It cannot represent "chosen type" unless the choice is already stored somewhere.

Stored continuous-effect ledger is appropriate later for 611.2 effects, timestamps, dependency, simultaneous ETB effects, and choices. It is too much for the first static additive L4 slice.

### Layer 4 vs Layer 4 + Layer 6

Layer 4 demand is higher (`layer:L4=10`) than Layer 6 (`layer:L6=2`). Also, Layer 4 affects more existing decisions: battlefield grouping, target legality, "is creature" SBA/combat checks, land play/cast menus, and snapshots. Layer 6 can reuse the same discovery machinery later, but ability grants have a wider semantic spread:

- Keyword-only grants can extend `effectiveKeywords`.
- Non-keyword ability grants require representing granted ability text in activation/trigger discovery.
- Ability removal and "can't have" effects require timestamp/override semantics under 613.9.
- Keyword counters are Layer 6 under 122.1b but use counter state rather than static source scanning.

Recommendation: keep Layer 6 out of Slice A unless the judge wants a very small attached keyword-only sub-slice. If included, it should be restricted to keyword additions only, with no removal, no "can't have", no quoted granted activated/triggered ability, and no duration.

### Single-object vs multi-object scope

Supported first-slice targets can be single-object because the affected object is derived directly:

- Self static effect: source id equals affected id.
- Aura/Equipment/Fortification-style effect: source `attachedTo` equals affected id.

Do not include anthem or watcher effects such as "Creatures you control are [type]" or "Other creatures you control have flying." Those require iterating changing object sets, controller filters, dependency with type-changing effects, and wider read-site migration.

### Defer honestly

The following should remain manual/deferred:

- Anthem or multi-object static effects: "Creatures you control get/have/are ..."
- Static effects with controller/color/type predicates over many objects.
- Any generated-by-resolution continuous effect under 611.2, including "until end of turn", "for as long as", "becomes", "gains", and 611.2e ETB-linked effects.
- Object-set locking under 611.2c.
- Variables captured on resolution under 611.2d.
- CDAs that must function in all zones under 604.3/604.3a, unless the judge explicitly makes all-zone effective characteristics part of Slice A.
- Chosen values such as "the chosen type" unless choice state already exists.
- Timestamp sorting and dependency under 613.7/613.8.
- Multiple same-layer effects where order can matter, including ability add vs ability remove and type set vs type add.
- Ability removal and "can't have/gain" Layer 6 effects.
- Text-changing Layer 3 under 612.
- Copy effects and L1a.
- Face-down L1b.
- Control-changing Layer 2; `effect.gain-control` is only an atom today.
- Color-changing Layer 5.
- P/T layers 7b/7c/7d from continuous effects. Existing +1/+1/-1/-1 counters remain separate ad hoc support under 122.1a/613.4c.
- Keyword counters under 122.1b unless a dedicated counter-to-keyword bridge is scoped.
- Basic land type implied mana abilities. For a test like Nylea's Presence, Slice A can verify type words only; adding mana abilities from basic land types is a separate rule area.
- Trigger/event snapshots becoming fully effective characteristic snapshots. If Slice A only changes live reads, ETB snapshot behavior may still lag.

## Recommended Slice Split

### Slice A: Read-Time Additive Layer 4 Type Accessor

Goal: introduce the first effective-characteristics read path without a stored continuous-effect ledger.

Scope:

- Pure function from `GameState + cardId` to effective type-line data.
- Battlefield permanents only.
- Additive Layer 4 static abilities only.
- Start with self effects and optionally attached-object effects.
- Migrate only named high-value read sites: engine `typeLineOf`, `typeLineForStateCard`/target legality, `isSummoningSick`, battlefield grouping, and context-menu checks that gate creature/land/planeswalker behavior.
- Tests use synthetic definitions and/or verified static oracle patterns.

Non-goal: full `computeEffectiveCharacteristics`, timestamps, dependencies, duration ledger, Layer 6, Layer 7, CDAs in nonbattlefield zones.

### Slice B: Keyword-Only Layer 6 Additions

Goal: reuse the static-effect discovery/query structure for keyword additions.

Scope:

- `effectiveKeywords(state, cardId)` includes supported static keyword grants from self/attached source.
- Keyword additions only.
- No ability removal, no quoted granted non-keyword abilities, no "can't have/gain", no keyword counters unless separately scoped.

Good candidates: "Enchanted creature has flying." and "Equipped creature has deathtouch and lifelink."

### Slice C: Stored Continuous-Effect Ledger

Goal: handle 611.2 generated effects and observable CR 613 ordering.

Scope:

- Duration records.
- Object-set locking.
- Variable capture.
- Timestamp assignment.
- Dependency ordering.
- Multi-layer effects preserving affected object sets under 613.6.

This is the first point where `activeContinuousEffects` or equivalent stored state becomes justified.

## Judge Decision Points

1. Pure read-time computation vs stored continuous-effect ledger.
   - Read-time fits static effects and current GameState-minimal style.
   - Stored ledger is necessary for 611.2 duration/timestamp/object-set-locking, but expands restore/backfill and schema risk.

2. Whether Slice A uses a real "layer" abstraction.
   - Option A: narrow `effectiveTypeLine`/type accessors with no public layer model.
   - Option B: introduce small internal effect descriptors tagged `L4` for future migration.
   - Avoid a dependency graph/timestamp engine until a supported case makes ordering observable.

3. Whether Layer 6 is in Slice A.
   - Defer: lower risk, lets L4 read-site migration settle first.
   - Include keyword-only: can reuse `effectiveKeywords`, but must be explicit that this is not general Layer 6.

4. Whether attached-object effects are in Slice A.
   - Include: `attachedTo` already exists and Auras/Equipment are single-object under 604.4.
   - Defer: self-only is smaller and avoids scanning attachments at every type query.

5. Whether CDAs are included.
   - Include CDAs only if all-zone characteristic reads are in scope.
   - Exclude unconditional self subtype-defining lines from battlefield-only Slice A to avoid violating 604.3.

6. Which read sites must migrate for acceptance.
   - Engine-only migration is easier but can leave UI and target picker inconsistent.
   - Gameplay-visible acceptance should require target legality, SBA/combat, battlefield grouping, and relevant menus to read the same accessor.

7. Static ability detection source.
   - Existing `splitAbilityLines`/`classifyAbilityShape` can identify static lines.
