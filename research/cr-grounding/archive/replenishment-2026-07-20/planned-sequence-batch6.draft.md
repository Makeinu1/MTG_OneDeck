# plannedSequence batch6 候補ドラフト — 2026-07-18 直接プレイ摩擦

Status: judge review required. This draft does not edit `docs/`, the ledger, or reviewer-owned tests.

## 0. ユーザーの真意として固定すること

2026-07-18 のユーザーコメントは、機能数を増やす要望ではなく、**カードを出す → 誘発を積む → 能力を使う → 次のカードを唱える**という一人回しの主ループを、詳細画面やフィードを経由せず連続して進めたいという直接プレイ摩擦の報告である。現行UIには「概ね満足」と明示されているため、全面再設計の根拠にはしない。現在の画面構成を保持し、以下4点の摩擦だけを主ループ側から直す。

特にマナ自動化は「対応カードが多い」だけでは足りない。1枚だけ対応外でも操作のリズムが切れるため、MyDeck 実プレイで使うマナ源については**カバレッジの完全性そのものが快感**になる。この直接証拠は `docs/judge-protocol.md` §2 の最上位信号に該当し、score.ts demand や既存の未着手 ACT-3/ACT-4 より先に照合する候補とする。

候補順はユーザーの列挙順を保存する。最終の台帳挿入・順序判断は判定者が行う。

## 候補1（最優先）: マナ能力カバレッジ完遂 + キャスト自動支払い

- **提案ID**: `ux-mana-complete-loop`
- **関連domain**: `cr-605-mana-abilities` / `cr-601-casting` / `cr-118-costs`
- **CR根拠**: 601.2f–h（総コスト確定・マナ能力を起動する機会・支払い）、602.2/602.2b（起動とコスト支払い）、605.1a（起動型マナ能力の定義）、605.3a–b / 405.6c（支払い中にも起動でき、スタックを使わず即時解決）、118.3/118.3c（全コストが必要・マナ能力の起動は任意）、305.6（基本土地タイプの固有マナ能力）。
- **直接プレイ摩擦**: 「土地やその他から自動ですべてのマナを出せることは非常に心地よいが、1枚でも未実装だと不快」「起動型能力のマナ能力を実装の中心にし、キャストの自動マナ計算も伴わせたい」。
- **現コードで確認した原因**:
  - `src/engine/autotap.ts` は `naiveTapManaColors()` が返す源だけを列挙する。
  - `src/engine/grammar/manaShortcut.ts` は shortcut を原則「全コストが `{T}` の行」に限定する。これは誤ったコスト踏み倒しを防ぐ安全策として正しいが、planner が一般の `activatedManaAbilityPlanForSource()` を使わないため、追加コスト付き、複数マナ、選択を伴うマナ源などが自動支払い候補から外れる。
  - `tapCommands()` は候補1つにつき常に1マナを足すため、マナ能力の実効果を planner が表現していない。
- **提案境界**:
  1. 最初に現在の MyDeck 群に実在する全マナ能力行を inventory 化し、`auto / guided / honest-manual` と非対応理由を可視化する。Scryfall 連携変更を伴う場合は実 API で再確認する。
  2. 自動支払い planner の source を `naiveTapManaColors` だけでなく、既存の `activatedManaAbilityPlanForSource` と同じ正規化済み能力計画へ統合する。planner は `{T}`、生け贄、ライフ、マナ、色選択、複数マナをコストと効果の一体 transaction として評価する。
  3. 「唱える」操作は、既存プール + 利用可能なマナ能力の組合せから決定的な支払い案を作り、一度の undo でキャスト前へ戻せる単一操作にする。曖昧な選択だけ guided UI を出す。
  4. `118.3c` に従い自動起動を強制ルールにはしない。手動支払い・別のマナ源を選ぶ経路と sandbox 強行を残す。
  5. MyDeck inventory の対応可能な全源が `auto` または `guided` になり、黙って候補から消える源を0件にする。未対応はカード上で理由と手動起動導線を表示し、見かけだけの100%を作らない。
- **受け入れ草案**:
  - 土地、マナ・クリーチャー、マナ・アーティファクト、複数マナ源、色選択源、追加コスト付き源を含む MyDeck 実例で、キャストが正しい能力起動と支払いを1操作で行う。
  - マナ能力は通常スタックへ置かれない。通常の起動型能力との表示・実行経路を混同しない。
  - 支払い不足、タップ済み、召喚酔い、起動制限、未解釈コストを成功扱いしない。強行時は non-CR-legal を記録する。
  - undo/redo、決定性、構造共有、旧snapshot互換を維持する。

## 候補2: 誘発をフィードから分離し、主操作とショートカットを直結

- **提案ID**: `ux-trigger-direct-loop`
- **関連domain**: `cr-603-triggered-abilities` / `cr-117-priority`
- **CR根拠**: 603.3（次に優先権を得る直前に誘発をスタックへ）、603.3b（複数誘発のtwo-bucket + APNAP + controller order）、603.3c–d（モード・対象等はスタックへ置く時に選ぶ）、603.6a（ETB誘発）、117.5（SBA → 誘発配置の固定点）。
- **直接プレイ摩擦**: 戦場へ出した後の誘発が上矢印ショートカットで処理されず、「誘発処理 → フィード → スタック」という三段階が直感的でない。
- **現コードで確認した原因**:
  - `ThumbZone` の主ボタンは誘発候補時に `openFeed()` する。
  - `gameController` の `useShortcuts.onNextPhase` はスタックの有無だけを見て、誘発候補を見ずに `advancePhase()` へ進む。主ボタンとショートカットが別の状態機械になっている。
  - `Feed` がログ/警告という受動情報と、誘発をスタックへ置く能動操作を兼務している。
- **提案境界**:
  1. 主ボタンと上矢印を同じ `runPrimaryAction` に束ねる。状態優先度は `stack resolve > pending trigger placement > attack > phase advance` の単一正本にする。
  2. 誘発が1件で、順序・モード・対象等の選択が不要なら、主操作/上矢印から直接 `placePendingTriggersForPriority` 相当のCR準拠経路へ置く。
  3. 複数件または選択が必要なら、フィードではなく専用の「誘発」シートを直接開き、順序・モード・対象を完了してからまとめてスタックへ置く。
  4. 配置後はスタック帯へ視線を移し、主操作を即「解決」に変える。Feed はログ・警告の履歴に戻し、誘発処理の必須中継点にしない。
  5. pending trigger がある間にフェイズ移動しない。silent dismiss もしない。
- **受け入れ草案**:
  - ETBで単一誘発が生じた直後、上矢印1回でスタックに置かれ、次の上矢印で解決へ進む。
  - 主ボタンとキーボードが全状態で同じ効果を持つ。
  - 複数誘発は603.3bの順序を保持し、不完全な並びを成功扱いしない。
  - Feedを一度も開かずに通常の誘発処理を完了できる。

## 候補3: カード上の smart tap / quick ability

- **提案ID**: `ux-ability-quick-action`
- **関連domain**: `cr-602-activated-abilities` / `cr-605-mana-abilities`
- **CR根拠**: 602.2–602.2b（能力の選択・スタック生成・コスト支払い）、605.1a / 605.3b（マナ能力は通常の起動型能力と異なりスタックを使わない）、118.3（支払えないタップコスト等を払えない）。
- **直接プレイ摩擦**: 右クリックして詳細へ入らないとタップ能力を含む能力選択に到達できず、自動化とUIが融合していないため、機能の存在自体に気づけない。
- **現コードで確認した原因**:
  - `GameCard` の戦場カード通常クリックは無条件で `toggleTap()`。
  - 能力の行選択は `CardActionSheet` 内の `ability-activate-*` にだけ存在する。
  - したがって「カードをタップした」ことと「{T}能力を起動した」ことがUI上で分断される。
- **提案境界**:
  1. 戦場カードの通常クリックを `smart tap` とする。CR準拠にモデル化できる `{T}` 能力がちょうど1本なら、その能力を起動してコストとしてタップする。単なる見た目のタップと能力起動を二重実行しない。
  2. 複数の `{T}` 能力がある、または能力解釈が manual の場合は推測せず、カード近傍の小さな quick ability picker を開く。
  3. 能力なしなら従来どおり手動タップ。生の手動タップ/アンタップは右クリック・Enterの全操作シートに常設し、sandbox操作を失わない。
  4. マナ能力は起動後すぐマナHUDへ結果を反映し、通常能力はスタック帯へ送る。アイコン・色・短いラベルでも両者を混同させない。
  5. キーボード、タッチ、右クリックの同等経路を維持する。
- **受け入れ草案**:
  - 単一の `{T}: Add ...` 源はカード1クリックでタップ+マナ生成。
  - 単一の非マナ `{T}: ...` 能力はカード1クリックでコスト支払い+能力をスタックへ。
  - 複数能力では勝手に先頭を選ばず、1操作で選択UIが出る。
  - 手動タップは常に代替経路から実行可能。

## 候補4（候補1–3の横断制約）: レスポンシブな action language

- **提案ID**: `ux-responsive-action-language`
- **関連domain**: design/UI。レイアウト自体を一意に定めるCR条文はない。
- **CR意味境界**: 602.2 / 603.3 / 605.3b の違い（通常能力を起動、誘発を置く、即時解決するマナ能力）は、アイコン化しても消してはならない。
- **直接プレイ摩擦**: 日本語の説明文はデスクトップとモバイルで幅への感度が大きく、モバイルで2行化・あふれ・機械的な印象が生じる。漢字2文字程度の短ラベルは問題が少なく、反復操作はアイコンへ置き換えたい。
- **専門提案**:
  1. **反復操作は icon-first**: 解決、誘発、起動、タップ、フェイズ、ターン、undo/redo、墓地/追放/ライブラリ等に24pxグリッドの統一アイコンを割り当てる。
  2. **意味を文章から消さない**: アイコン単独にするのは学習済みの反復操作だけ。初見・危険・不可逆寄りの操作は `icon + 漢字2–4文字`。長い説明は常設ボタンから外し、初回ヒント、tooltip、詳細シート、警告に置く。
  3. **幅で情報量を変える**: mobileはアイコン+短ラベル、desktopは同じアイコン+補助ラベル。DOM上の操作と `aria-label` は同一に保ち、CSSだけで補助文字を省略する。
  4. **状態は形だけに頼らない**: active/disabled/warning/stack/mana を色、形、`aria-pressed`/`aria-disabled`、短い状態語で重ねて示す。色やアニメーションだけに依存しない。
  5. **一括置換しない**: ルール説明や警告まで絵文字化すると意味が曖昧になる。まず候補1–3の主ループに限定してアイコン体系を作り、375px縦 / 812px横 / 1440pxで文字あふれ0を実測してから広げる。
- **受け入れ草案**:
  - 3形態すべてで主操作が1行に収まり、横方向の文字あふれ・意図しない2行化が0。
  - アイコンだけを見ても、tooltip/aria-label/短ラベルのいずれかで意味を確認できる。
  - prefers-reduced-motion、200%相当の文字拡大、キーボードfocusでも操作を識別できる。
  - 新規コンソールエラー0件。

## defer / 非目標

- 全Scryfallカードのマナ能力100%自動化を初回スコープにしない。最初のhard gateはMyDeck実カード100% inventory + 対応可能形のauto/guided化である。
