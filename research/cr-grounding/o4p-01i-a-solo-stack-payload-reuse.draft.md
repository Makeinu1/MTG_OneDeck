# O4P-01I-A Solo stack payload reuse matrix (draft)

- Milestone: `O4P-01I-A`
- Role: Architecture Analyst
- Analysis anchor supplied by task: `PLAN_SHA=5418d82`
- Scope: read-only survey of the current Solo engine/store and existing tests; no
  implementation, contract freeze, export integration, ledger update, or Online
  runtime work.
- Classification vocabulary is exact: `SHARE_DIRECT`, `ADAPT`, `SOLO_ONLY`,
  `REFACTOR_BEFORE_CORE`, `REJECT`.
- “Semantic reuse” means reuse of the meaning represented by the current Solo
  value, not reuse of its mutable object or command implementation.

## Findings first

The Solo stack is represented by a `CardInstance` stored in `GameState.cards`,
with stack order derived from `GameState.zones.stack`. The same object shape
contains physical-card runtime, spell choices, ability identity, activation
cost data, trigger condition data, and resolution text. `castToStack` and
`addAbilityToStack` are command payloads, but their current implementations
commit directly into the Solo `GameState`; the store actions additionally own
proposal/payment/target prompting and pending-trigger consumption.

The O4P-01H mode-neutral core already has a separate, immutable stack-object
identity representation (`src/engine/core/object/stackObjectV2.ts`). It is
useful for object kind, controller, source identity, ability key, and historical
copy provenance. It does not contain announcement choices, targets, costs,
resolution text, trigger conditions, or stack order. That is a deliberate gap,
not evidence that `CardInstance` can be aliased into Online state.

The strongest reuse boundary is therefore: reuse canonical references and
choice meaning after conversion into fresh readonly records; do not share the
Solo `CardInstance`, `GameCommand`, store action, or resolver by alias. In
particular, copy handling is not alias-safe: spell copies clone selected
choices and `announcedX`, ability copies rebuild an ability object, and
resolution can turn a permanent spell copy into a token or make a nonpermanent
copy cease to exist.

## Required guardrails for the next contract

1. Do not alias a Solo `CardInstance`, `TargetSelection[]`, `ObjectSnapshot`,
   `ActivationEnvelope`, `PendingTrigger[]`, or copied ability object into the
   mode-neutral core. Convert to fresh readonly values and deep-freeze nested
   arrays/records.
2. Do not treat `GameCommand` or a store action as the Online authority record.
   Payment, proposal, prompt, legality, priority, and resolution remain outside
   this committed-only slice.
3. Preserve bottom-to-top stack order from the existing stack sequence; do not
   add a second order field to a payload.
4. Preserve historical object references even when the source is no longer in
   the registry. A physical id alone is insufficient for target/source identity.
5. Copy is a new stack object with copied announcement choices, never an alias.
   Spell-copy and ability-copy records require separate construction rules.
6. `forced`, `unchecked-warning`, parser status, and local trigger-candidate
   presentation are not Online legality or decision authority.

  `applyAddAbilityToStack`, `resolveTopStack`/`resolveStackTop`, copy handling,
  `pendingTriggers`, `triggerCondition`, `abilityResolutionText`, `announcedX`,
  and `targetSelections`.
- No implementation or test command was run; this is an architecture survey.
- No claim is made that the current Solo structures are safe for direct Online
  reuse. The direct-share count is zero by design.
- Findings: current Solo payload values are semantically valuable but are not
  canonical mode-neutral records; the next contract must introduce explicit
  immutable conversion/validation and keep lifecycle authority out of O4P-01I.
